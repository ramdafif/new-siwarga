# Audit SiWarga - 27 Oktober 2026

## Ruang lingkup dan status

Audit dilakukan pada Capstone2, termasuk perubahan 405 dari sesi sebelumnya.
Pemeriksaan mencakup routing/form HTML, autentikasi/sesi/rate limit, otorisasi
wilayah dan foto, alur tiket/notifikasi, validasi input, transaksi, unggahan,
backup/restore, template deployment/monitoring, dependency terkunci, dan browser.
Tidak ada perubahan kode aplikasi dalam audit ini. Temuan di bawah masih terbuka.
Probe mutasi dijalankan hanya pada database khusus test, bukan database aplikasi.

P1 berarti perlindungan keamanan perlu diprioritaskan sebelum pemakaian resmi.
P2 adalah gangguan fungsi/operasional yang perlu diperbaiki. P3 adalah masalah
konsistensi data dengan urgensi lebih rendah. Tidak ditemukan bukti pengambilalihan
akun tanpa password atau cookie, dan audit ini bukan sertifikasi bebas kerentanan.

## Temuan

### A01 - P1: pembatasan login per akun dapat dilewati dengan alias kolasi

- Lokasi: app/auth.py:25, app/auth.py:33, app/security.py:120,
  scripts/configure_local.py:24.
- Key limiter memakai email input setelah strip/lower, sedangkan pencarian user
  mengikuti kolasi MySQL utf8mb4_unicode_ci yang menganggap beberapa huruf
  beraksen setara dengan huruf tanpa aksen.
- Reproduksi: lima password salah untuk owner@example.com, lalu login melalui
  alias berawalan U+00F3, yaitu o beraksen. Database memilih user yang sama,
  tetapi key limiter berbeda. Dengan password yang benar, hasilnya 302 alih-alih
  429 meskipun akun tersebut sudah mencapai batas lima percobaan.
- Dampak: batas per akun tidak melindungi identitas yang sama secara konsisten.
  Batas per IP masih berlaku; ini bukan login tanpa password. Risiko meningkat
  jika penyerang memiliki banyak IP.
- Rekomendasi: samakan definisi identitas untuk lookup, uniqueness, dan limiter;
  jangan hanya melakukan normalisasi Unicode yang berbeda dari kolasi database.
  Pilihan implementasi perlu mencakup kompatibilitas akun Unicode yang sudah ada.

### A02 - P1: cookie sesi sebelum logout masih dapat dipakai ulang

- Lokasi: app/auth.py:99, app/__init__.py:105, app/security.py:150.
- Logout hanya membersihkan cookie di browser yang keluar. Tidak ada pencabutan
  sisi server untuk sesi tersebut; account_version tetap valid.
- Reproduksi: salin cookie milik akun test sebelum logout, logout normal, lalu
  pasang cookie lama di client terpisah. GET /dashboard tetap menghasilkan 200.
- Dampak: jika cookie sudah dicuri, logout tidak menghentikan akses pemegang
  salinannya. Akses masih dibatasi masa berlaku dan pencabutan versi akun akibat
  reset password/perubahan akun; penyerang tetap membutuhkan cookie yang valid.
- Rekomendasi: gunakan ID sesi yang dapat dicabut per sesi di server. Menaikkan
  account_version saat logout adalah alternatif lebih sederhana, tetapi akan
  mengeluarkan semua sesi akun, bukan hanya perangkat yang logout.

### A03 - P2: template monitoring tidak cocok dengan trusted hosts produksi

- Lokasi: deploy/app.env.example:10, deploy/prometheus.yml:13.
- Konfigurasi aplikasi mempercayai siwarga.example.org saja, sementara Prometheus
  mengakses 127.0.0.1:8000 dengan Host loopback.
- Reproduksi: GET /metrics dengan konfigurasi trusted hosts contoh dan Host
  127.0.0.1:8000 ditolak 400 sebelum handler metrics dijalankan. Probe memakai
  respons HTTP bawaan sementara untuk memisahkan temuan ini dari A04.
- Dampak: template deployment apa adanya tidak dapat mengumpulkan metrics
  aplikasi. Ini diuji pada konfigurasi contoh, bukan klaim tentang VPS yang hidup.
- Rekomendasi: selaraskan host scrape dan allowlist terbatas, pertahankan pemeriksaan
  alamat loopback dan pemblokiran endpoint metrics pada Nginx publik.

### A04 - P2: penolakan Host yang tidak dipercaya merusak renderer error

- Lokasi: app/__init__.py:157, app/templates/base.html:10.
- Invalid Host menyebabkan URL adapter tidak terbentuk. Handler HTTP tetap
  merender template yang memanggil url_for untuk asset dan navigasi.
- Reproduksi: request /health/live dengan Host yang tidak dipercaya menghasilkan
  AttributeError pada url_for, bukan respons 400 yang utuh. Renderer 500 juga
  bergantung pada template dasar yang sama.
- Dampak: request yang seharusnya ditolak dengan aman justru memicu exception
  tambahan dan log error; kasus A03 ikut mengalami masalah ini.
- Rekomendasi: sediakan fallback respons mandiri tanpa url_for/template dasar
  ketika URL adapter tidak tersedia, tanpa melemahkan TRUSTED_HOSTS.

### A05 - P2: email duplikat saat membuat pengurus menghasilkan 500

- Lokasi: app/admin.py:142, app/admin.py:147, app/admin.py:16.
- db.session.flush dijalankan sebelum memasuki penanganan IntegrityError di save.
- Reproduksi: buat pengurus memakai email yang sudah terdaftar. Hasilnya 500,
  padahal konflik sejenis di master data diterjemahkan menjadi 409.
- Dampak: input admin yang wajar memunculkan halaman gangguan server, bukan
  penjelasan konflik. Tidak terbukti ada akun duplikat yang tersimpan.
- Rekomendasi: bungkus seluruh flush dan commit pada batas transaksi yang sama,
  lakukan rollback, dan kembalikan pesan konflik yang konsisten.

### A06 - P2: query string dapat bertabrakan dengan argumen internal url_for

- Lokasi: app/tickets.py:94, app/templates/components.html:76.
- Seluruh request.args diteruskan sebagai keyword arguments ke url_for.
- Reproduksi: GET /pengaduan?endpoint=anything dan
  GET /pengaduan?_method=DELETE masing-masing menghasilkan 500.
- Dampak: URL dengan parameter tambahan dapat merusak daftar. Macro pagination
  menggunakan pola yang sama pada daftar lain ketika pagination tampil.
- Rekomendasi: hanya teruskan parameter filter publik yang dikenal, pisahkan
  parameter routing dari query, dan jangan meneruskan opsi internal Flask.

### A07 - P2: batas tanggal dan nomor halaman dapat memicu 500

- Lokasi: app/tickets.py:84, app/tickets.py:88.
- Reproduksi pertama: GET /pengaduan?dari=0001-01-01 memicu overflow saat
  mengurangi tujuh jam; handler hanya menangkap ValueError.
- Reproduksi kedua: page dengan angka puluhan digit diteruskan sebagai offset
  pagination dan berakhir dengan error query database.
- Dampak: input filter yang di luar rentang tidak menjadi 400 atau halaman aman.
- Rekomendasi: validasi rentang tanggal yang kompatibel dengan database dan zona
  waktu, serta batasi page/offset sebelum membangun query. Jangan mematikan
  validasi atau mengandalkan catch semua exception sebagai satu-satunya solusi.

### A08 - P2: notifikasi lama mengarahkan mantan petugas ke 404

- Lokasi: app/routes.py:67, app/routes.py:74.
- Reproduksi: buat notifikasi bertaut tiket untuk Karang Taruna, alihkan tugas ke
  anggota lain, kemudian tekan tombol pada notifikasi lama. Redirect berakhir 404.
- Pemeriksaan izin tiket tetap benar: mantan petugas memang harus kehilangan
  akses. Yang rusak adalah tujuan navigasi dari notifikasi pribadinya.
- Rekomendasi: periksa scope tiket terkini sebelum redirect. Bila akses sudah
  berubah, kembalikan ke daftar notifikasi dengan pesan yang sesuai, tanpa
  membuka kembali izin pada tiket.

### A09 - P3: nomor wilayah dengan nol di depan tidak dinormalisasi penuh

- Lokasi: app/admin.py:25, app/admin.py:29.
- Reproduksi: ketika RW 01 sudah ada, membuat RW 001 tetap berhasil dengan 302.
  zfill hanya menambah panjang minimum, bukan mengubah representasi ke nomor
  kanonis. Validator yang sama dipakai untuk RT.
- Dampak: dua ID wilayah dapat mewakili nomor numerik yang sama, berpotensi
  membingungkan pilihan wilayah dan administrasi akun.
- Rekomendasi: format kembali dari nilai integer, lalu periksa konflik. Tinjau
  data yang sudah ada sebelum normalisasi/migrasi agar tidak menggabungkan scope
  pengguna secara tidak sengaja.

## Bukti pengujian

- Probe khusus audit: 11 kasus gagal sesuai perilaku yang masih bermasalah;

  ditemukan, tanpa dependency yang dilewati. Sumber: test-results/audit/
  dependencies.json. Ini tidak menyatakan kode aplikasi aman atau advisory
  masa depan tidak akan muncul.
- git diff --check dijalankan; tidak ada error whitespace.
- compileall pada aplikasi, scripts, tests, dan probe audit lulus.


## Batas audit dan urutan perbaikan

Audit ini bukan pentest server publik. Belum memvalidasi Nginx/systemd pada Linux,
TLS/domain/firewall aktual, Redis produksi, pengiriman alert, repository backup
remote, restore lintas mesin/RTO, atau soak test dua jam. Backup lokal dan isolasi
otorisasi diuji oleh suite yang sudah ada. Tidak ada load test mutasi ke aplikasi
pengguna. Risiko performa detail dengan koleksi komentar/riwayat yang terus
bertambah masih memerlukan pengukuran skala nyata.

Prioritas: A01/A02, kemudian A03/A04, A05-A07, A08, lalu A09. Sesudah perbaikan,
pindahkan probe yang relevan menjadi regresi permanen, jalankan ulang suite dan
browser, lalu verifikasi deployment staging secara terpisah.
